## Configuration allocation, draft creation and lifecycle

Configuration versions begin at `1` for each Unit Type. Allocation belongs only to `UnitTypeConfigurationService`; `findLatestVersionNumberForUnitType()` remains observational and must never become an allocator.

Allocation locks the Unit Type as the serialization root, increments `last_allocated_configuration_version`, and creates the DRAFT in the same transaction. A successfully committed creation permanently consumes its version. Deleting that DRAFT later does not make the number reusable. A rollback before successful creation rolls the allocation back. `MAX(version_number) + 1` is prohibited.

Per Unit Type there may be at most one ACTIVE, one DRAFT, and any number of HISTORICAL configurations. An existing DRAFT fails with `CONFIGURATION_DRAFT_ALREADY_EXISTS`.

New configurations always begin DRAFT. Draft creation supports:

1. A blank DRAFT, permitted whether or not an ACTIVE configuration exists.
2. A deep clone of the current ACTIVE configuration. It copies Measurement and Attribute Rule rows, reuses canonical Definition references, and excludes configuration identity, ULID, status, version number, timestamps and actor metadata. Clone plus allocation plus DRAFT creation is one transaction. Cloning fails with `NO_ACTIVE_CONFIGURATION` when there is no ACTIVE configuration.

Arbitrary historical cloning, cross-Unit-Type cloning and DRAFT-to-DRAFT cloning are out of scope.

The only normal lifecycle is:

```text
DRAFT -> ACTIVE -> HISTORICAL
```

Only DRAFT structure is editable. Activation is an explicit transactional operation: lock Unit Type, then target Configuration, then rule rows only when needed. Never reverse this order. Activation revalidates the complete structure inside its transaction; it cannot trust prior DRAFT checks. A newer activated DRAFT changes the existing ACTIVE configuration to HISTORICAL. ACTIVE and HISTORICAL configurations and their structural rules are immutable and never hard-deleted. DRAFT cannot normally go directly to HISTORICAL; ACTIVE cannot return to DRAFT; HISTORICAL cannot return to ACTIVE or DRAFT. An eligible DRAFT may be hard-deleted. Restoring historical structure requires a new version.

## Catalog lifecycle, identity and provenance

Canonical catalog status is `ACTIVE` or `INACTIVE`. ACTIVE records are available for new operational use. INACTIVE records preserve historical references but cannot be newly used. Deactivation is not deletion and never cascades status changes.

ULID and canonical code are immutable after creation. Services normalize new codes as `trim + uppercase`. Arabic and English labels and approved display metadata remain editable.

| Provenance | Edit | Deactivate / reactivate | Hard delete |
| --- | --- | --- | --- |
| `SYSTEM_SEED` | Allowed | Allowed | Forbidden |
| `SYSTEM_ADMIN` | Allowed | Allowed | Only if unreferenced and audit-safe |

Database RESTRICT is the final integrity defense. Services must apply business eligibility before deletion or deactivation. A Definition referenced by an ACTIVE configuration cannot deactivate if that would invalidate the configuration. INACTIVE Definitions cannot enter new DRAFT structures or activated configurations. A Category cannot deactivate while it has ACTIVE Unit Types. A Unit Type cannot reactivate while its Category is inactive. Unit Type deactivation does not automatically alter its ACTIVE configuration.

## Definitions, Options and configuration rules

Definitions introduced into a new DRAFT must be ACTIVE. Duplicate Measurement or Attribute Definition rules within a Configuration are forbidden.

Measurement Rules are `REQUIRED` or `OPTIONAL`; `primary=true` requires `REQUIRED`; at most one primary Measurement is allowed; zero primaries is legal. DRAFT add, update, remove and reorder operations must preserve these invariants atomically.

Attribute Rules are `REQUIRED` or `OPTIONAL`. No rule means NOT APPLICABLE. Datatype belongs to the Attribute Definition and cannot be overridden by a Configuration Rule. Supported datatypes are `INTEGER`, `DECIMAL`, `BOOLEAN`, `TEXT`, `ENUM`, and `DATE`.

Options belong to Attribute Definitions, not Configuration Versions. Only ENUM Definitions may have Options. An ENUM Definition used by DRAFT creation or activation must have at least one ACTIVE Option. A mutation must not leave an ENUM used by an ACTIVE configuration with zero ACTIVE Options. Attribute datatype is immutable after creation. Options may become INACTIVE without rewriting historical data.

Rule mutations on ACTIVE or HISTORICAL configurations fail with the structural immutability error. Activation repeats validation of the Unit Type/catalog statuses, Definitions, primary rules, ENUM semantics and Configuration state inside its transaction.

## Geography hierarchy and lifecycle

Geographic types, in ascending order, are `COUNTRY`, `GOVERNORATE`, `CITY`, `AREA`, and `DISTRICT`. Level skipping is allowed, but a parent must be a higher level. Same-level and reversed-level parent relationships are forbidden. COUNTRY has no parent; every other type requires one. Type, code and ULID are immutable after creation.

Parent reassignment is allowed only after full validation: self-parent and cycles are forbidden. Reuse BF014.2 iterative ancestry behavior; no recursive CTE is required. Structural hierarchy changes are transactional and serialize by locking the Country/root first. Reads require no hierarchy lock.

A parent cannot deactivate while active descendants exist. A child cannot reactivate while any ancestor is inactive. No status changes cascade, and historical references survive deactivation.

## Development Catalog lifecycle

The V1 model is `Developer -> Project -> Phase`. A Project may have a nullable `developer_id` and nullable `geographic_location_id`. A Phase belongs to exactly one Project and has no independent Geography. Project Developer and Geography references may be assigned, removed or reassigned, but new/reassigned references must be ACTIVE. Phase `project_id` is immutable after creation.

A Developer with ACTIVE Projects cannot deactivate. A Project with ACTIVE Phases cannot deactivate. A Phase cannot reactivate under an INACTIVE Project. A Project linked to an INACTIVE Developer cannot reactivate until the Developer becomes ACTIVE or the relationship is removed/reassigned. Geography deactivation does not alter Project status; no catalog status operation cascades.

Developer is the lock root for operations that race with Project attachment or deactivation. Project is the lock root for operations that race with Phase creation or deactivation. Property inference and completeness behavior are outside BF014.3.
