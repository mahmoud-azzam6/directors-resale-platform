## Runner and ledger

One explicit project CLI entry point bootstraps the existing container and invokes one BF014 runner; it is never an HTTP endpoint or automatic application-boot action. The runner discovers registered packages, prints package key/progress and a concise failure result, and exits non-zero on failure. B1 registers and runs packages `001` Categories and `002` Unit Types in numeric order. Packages `003` Measurements, `004` Attributes, `005` Options, `006` Configurations + Rules, and `007` Egypt Geography remain planned only.

Migration 030 provides `property_catalog_seed_versions`: unique `seed_key`, `checksum`, `applied_at`, and optional `applied_by_user_id`. A minimal BF014.5 ledger repository only finds an applied key/checksum and records a successful application. One transaction covers one package: resolve earlier dependencies, validate collisions, create data, insert ledger record, commit. A failure rolls back that package, records no ledger row, stops later packages, and leaves earlier committed packages intact. A retry skips prior successes and retries the failed package.

Packages are immutable. A successful key is skipped only when its checksum matches; a changed applied package fails deterministically and requires a new numbered package/version. Package idempotency is ledger skip; data idempotency resolves every dependency by stable business code, never generated IDs or cross-package ULIDs. Reruns never reconcile labels, status, or legitimate System Admin edits.

Before applying a package, a matching compatible `SYSTEM_SEED` identity is acceptable only when it exactly matches the package’s expected shape; a matching `SYSTEM_ADMIN` code, incompatible type/relationship, or ambiguous identity fails without takeover or overwrite. Every baseline row uses `SYSTEM_SEED` where supported. Seeded records retain normal editable/lifecycle rules but cannot be hard-deleted.

## Provenance implementation rule

Outcome A applies to Categories, Unit Types, Measurement Definitions, Attribute Definitions, and Attribute Options: each public creation API accepts a data array and `createCatalog()` accepts controlled `SYSTEM_SEED` or `SYSTEM_ADMIN` provenance, defaulting to `SYSTEM_ADMIN`; provenance remains immutable after creation. No extension is required for those records. Configuration creation is different: `createBlankDraft()` and clone creation hardcode configuration provenance to `SYSTEM_ADMIN` and expose no provenance argument. BF014.5A therefore requires a narrow controlled provenance argument for configuration DRAFT creation only, constrained to `SYSTEM_ADMIN` and `SYSTEM_SEED`, defaulting to current `SYSTEM_ADMIN`; rules and activation retain current behavior. The runner must use this Service extension, never repositories or direct SQL.

Migration 030 already supplies a unique `seed_key` (one applied record per key), a required `CHAR(64)` checksum constrained to 64 hexadecimal characters, and `applied_at`. It supports the immutable-package checksum contract; no additive schema migration is required for BF014.5.
