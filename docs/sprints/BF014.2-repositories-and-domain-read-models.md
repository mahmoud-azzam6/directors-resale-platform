## Repository and read-model architecture

Exactly six repositories implement BF014.2:

1. [PropertyCatalogRepository](../../app/Modules/Property/Repositories/PropertyCatalogRepository.php)
2. [MeasurementDefinitionRepository](../../app/Modules/Property/Repositories/MeasurementDefinitionRepository.php)
3. [AttributeDefinitionRepository](../../app/Modules/Property/Repositories/AttributeDefinitionRepository.php)
4. [UnitTypeConfigurationRepository](../../app/Modules/Property/Repositories/UnitTypeConfigurationRepository.php)
5. [GeographicLocationRepository](../../app/Modules/Property/Repositories/GeographicLocationRepository.php)
6. [DevelopmentCatalogRepository](../../app/Modules/Property/Repositories/DevelopmentCatalogRepository.php)

The `property_catalog_seed_versions` repository is NOT part of BF014.2. Seed ledger persistence remains deferred to BF014.5.

Repositories provide data access and persistence primitives with explicit query/list contracts, stable PHPDoc associative-array read models, and no hidden joins by default. Database errors propagate. Repositories do not own authorization, business workflows, multi-step transactions, ULID generation, canonical code normalization, or lifecycle decisions. Services remain responsible for business orchestration.

The intentional read-model strategy uses repository-specific PHPDoc associative arrays instead of ORM entities, a heavy DTO hierarchy, or a generic domain entity layer. Implemented read models are:

- PropertyCategoryRecord, UnitTypeRecord
- MeasurementDefinitionRecord
- AttributeDefinitionRecord, AttributeOptionRecord
- UnitTypeConfigurationRecord, MeasurementRuleRecord, AttributeRuleRecord, UnitTypeConfigurationAggregate
- GeographicLocationRecord, GeographicAncestryRead
- DeveloperRecord, ProjectRecord, ProjectPhaseRecord

IDs and foreign IDs map to integers; nullable references and actor IDs remain integer-or-null. Sort order and applicable text maximum length map to integers, with nullable text limits preserved. Timestamps are strings. Measurement Rule `is_primary` maps strictly from `0` or `"0"` to false and `1` or `"1"` to true; all other representations, including PHP booleans and null, cause RuntimeException.

## Property Catalog and Definition persistence

PropertyCatalogRepository provides Category ID/ULID/code lookups, code existence checks, filtered lists and create/update/delete. Unit Types have the same primitives, category-scoped listing and `findUnitTypeForUpdate()`. Category reassignment is a mechanical persistence primitive; business eligibility belongs to Services.

MeasurementDefinitionRepository provides ID/ULID/code reads, code existence checks, batch ID reads, filtered lists and CRUD. AttributeDefinitionRepository provides the equivalent Definition operations, including a data-type filter. Attribute Options have global ID/ULID reads, Definition-scoped code lookup/existence and listing, create under a Definition, and Definition-scoped update/delete. Batch Options for Definitions are explicit; ordinary Definition reads do not automatically hydrate Options. Empty batches skip SQL; batch results use deterministic ordering.

## Configuration Versions and rules

UnitTypeConfigurationRepository provides ID/ULID lookup, Unit Type plus version lookup, active configuration lookup, ordered lists, CRUD and `findConfigurationForUpdate()`.

`findLatestVersionNumberForUnitType()` returns the highest currently persisted version number, or zero when none exists. It does not add one, allocate, reserve, or enforce never-reuse. Deleting the highest persisted version changes the result. Version allocation remains a BF014.3 Service design concern.

Measurement and Attribute Rules provide configuration-scoped CRUD, scoped ID/Definition lookup and deterministic `sort_order ASC, id ASC` lists. Update, reread and delete use both configuration ID and rule ID. Measurement Rules apply the strict boolean mapping described above. No draft-only editing policy is implemented in repositories. Database uniqueness, FK restrictions and generated active/primary guards remain the integrity boundary.

`findConfigurationAggregateById()` returns this structure, or null for a missing configuration:

```text
configuration: UnitTypeConfigurationRecord
measurement_rules: [ { rule, definition } ]
attribute_rules: [ { rule, definition, options } ]
```

It reads the configuration, Measurement Rules, Attribute Rules, Measurement Definitions in one batch, Attribute Definitions in one batch, and Options in one batch. Empty rule collections skip their metadata batches. Definitions are indexed by ID; Options are grouped by Definition ID. Rule ordering is preserved, inactive persisted metadata remains present, and Options may be empty. A missing referenced Definition causes RuntimeException. There is no per-rule N+1 hydration. Real MariaDB acceptance verified six queries with 51 Measurement Rules plus 51 Attribute Rules, three queries for an empty configuration, and one for a missing configuration.

## Geography and ancestry

GeographicLocationRepository provides ID/ULID/global-code lookup, code existence checks, filtered lists, direct children reads and CRUD. GeographicLocationRecord exposes `location_type`, mapped from physical DB column `type`; no schema rename occurred.

The parent filter contract is: omitted `parent_id` means unrestricted; explicit null means `IS NULL`; a numeric ID means equality. These semantics also work with search. `listChildren()` returns only direct children with supported status/type/search filters and deterministic ordering.

`loadAncestry(locationId, maxDepth=32)` returns `locations` and `stop_reason`. Stop reasons are `root`, `missing_parent`, `cycle`, and `depth_limit`. Traversal is iterative, starts with the requested row, and never appends a repeated cycle node again. The depth bound counts returned locations and accepts 1-256. A root at the bound returns `root`; a known repeated node is detected before the depth-limit stop. There is no recursive CTE, hierarchy mutation workflow, or repository cycle-prevention policy.

## Development Catalog

DevelopmentCatalogRepository provides Developer ID/ULID/code reads, existence checks, lists and CRUD. Projects provide the same operations with optional Developer and Geography references, including mechanical reassignment. For either nullable Project filter, omission means unrestricted, explicit null means `IS NULL`, and a numeric ID means equality. Combined filters and grouped search preserve these distinctions.

Project Phases have global ID/ULID reads, Project-scoped code lookup/existence, Project-scoped creation/listing/update/delete, and immutable Project ownership. Scoped update rereads also honor the Project ID. Codes may repeat across Projects but remain unique within a Project. No hidden joins are introduced.

## Search, pagination and writes

Catalog search is literal substring matching over `code`, `name_ar`, and `name_en`. `%`, `_`, and `!` are escaped with `!`, using an explicit `ESCAPE '!'` clause. SQL structure is fixed; values are prepared/bound and no user-controlled SQL identifiers or operators are accepted. Grouped OR search preserves accompanying filters. QueryBuilder handles supported ordinary queries; fixed prepared SQL handles grouped search and nullable predicates it cannot express.

Paginated lists default to limit 50 and offset 0; limits are 1-200 and offsets nonnegative. Catalog ordering is `sort_order ASC, id ASC`; Configuration Versions use `version_number DESC, id DESC`. Rule and aggregate batch reads are not implicitly paginated.

Writes use associative arrays and explicit allowlists. Unknown/read-only fields are rejected before query construction. Generated row IDs, timestamps and generated guards cannot be caller-written. Required foreign references are supplied through allowed create fields or scoped method arguments. ULID, stable code, provenance and creation attribution are immutable after creation. Scoped child ownership is immutable; explicitly supported Unit Type category and Project reference reassignments remain mechanical primitives. Configuration Unit Type and version number are immutable.

Empty updates reread without issuing UPDATE. Unchanged updates return the persisted record; zero affected rows are not interpreted as absence. Missing update targets return null; deletes return whether a row was deleted. Database restrictions protect referenced rows; repositories do not decide lifecycle eligibility.

## Transactions and locks

Caller/Service owns begin, commit and rollback; repositories never own multi-step transactions. Implemented locking helpers are PropertyCatalogRepository::findUnitTypeForUpdate() and UnitTypeConfigurationRepository::findConfigurationForUpdate(). No Geography/Developer/Project/Phase lock helpers exist. Callers also own any transaction needed for a consistent aggregate or ancestry snapshot.

Real MariaDB acceptance used two independent DatabaseManager/PDO connections to prove configuration `FOR UPDATE` blocking and release after both commit and rollback. A one-second lock wait timeout bounded blocking. Caller rollback and QueryBuilder lock-flag reset after success and failure passed. Validation failures execute no SQL on observed paths, and successful queries follow terminal-operation failures without stale builder state.
