# BF014.6 — Dynamic Property Form Projection

**Document Type:** Architecture Contract

**Status:** ARCHITECTURE APPROVED / IMPLEMENTATION NOT STARTED

**Parent:** [BF014 Canonical Property Catalog Foundation](BF014-canonical-property-catalog-foundation.md)

---

## 1. Purpose and boundary

BF014.6 defines the read-only backend projections that a future Arabic-first Add Unit experience consumes. It makes the canonical catalog and the active Unit Type Configuration authoritative for fields, requiredness, primary measurement, data type, units, options, codes, labels, ordering, and configuration version.

The frontend owns rendering, RTL layout, localized display choice, convenience validation, and user-experience flow. It must not hardcode Apartment, Villa, or other type-specific rules. Backend validation remains authoritative when future Property persistence is selected.

This unit does not create Organization Properties, Property Measurements, Attribute Values, proposals, completeness calculations, media, frontend components, routes, controllers, migrations, schema, or seed data. It is an architecture contract only.

## 2. Endpoint and authorization contract

The future read endpoints are:

```text
GET /unit-types/{id}/property-form
GET /property-profile/core-form
```

Both endpoints require an authenticated caller with the existing `property_catalogs.view` capability. They are operational catalog reads, are not `SYSTEM_ONLY`, and perform no mutation. They follow the existing controller authorization flow and JSON error envelope; they introduce neither a new permission nor a parallel authorization mechanism.

The implementation path is:

```text
Controller -> authorization -> PropertyFormProjectionService -> existing services/repositories
```

Repositories remain persistence-only. A projection service may compose existing catalog, configuration, geography, and development read APIs, and may receive narrowly scoped read-model support where the existing APIs cannot provide a bounded projection without N+1 queries.

## 3. Unit Type property-form response

The conceptual successful response has this stable shape. Field names use the existing canonical `name_en` and `name_ar` convention rather than a second localization representation.

```json
{
  "unit_type": {
    "id": 0,
    "code": "APARTMENT",
    "name_en": "Apartment",
    "name_ar": "...",
    "category": {
      "id": 0,
      "code": "RESIDENTIAL",
      "name_en": "Residential",
      "name_ar": "..."
    }
  },
  "configuration": {
    "id": 0,
    "version_number": 1,
    "status": "active",
    "provenance": "SYSTEM_SEED"
  },
  "measurements": [
    {
      "definition_id": 0,
      "code": "BUILT_UP_AREA",
      "name_en": "Built-up Area",
      "name_ar": "...",
      "default_unit_code": "SQM",
      "required": true,
      "primary": true,
      "sort_order": 10
    }
  ],
  "attributes": [
    {
      "definition_id": 0,
      "code": "BEDROOMS",
      "name_en": "Bedrooms",
      "name_ar": "...",
      "data_type": "INTEGER",
      "required": true,
      "sort_order": 10,
      "options": []
    }
  ]
}
```

`configuration.id`, `configuration.version_number`, `configuration.status`, and `configuration.provenance` identify the authoritative configuration used to produce the form. The successful projection always has `status: active`; provenance is descriptive, not an authorization signal. The unit type identity is repeated only in the top-level `unit_type` object.

### Active configuration and lifecycle behavior

The projection first resolves the requested Unit Type. A missing Unit Type is a not-found response using the existing catalog not-found error convention. For this new-Property-entry projection contract, an inactive Unit Type is unavailable and `GET /unit-types/{id}/property-form` returns the existing `CATALOG_ITEM_INACTIVE` domain error.

That new-entry rule does not erase or hide the catalog entity from administrative or history reads where existing APIs allow it, and it does not invalidate historical Property references. Future edit and view flows for existing Properties may require a historical catalog representation; BF014.6 does not define those Property edit or history semantics.

For an active Unit Type, the projection uses exactly its current active configuration:

- if one exists, it produces the projection;
- if none exists, it returns deterministic `NO_ACTIVE_CONFIGURATION` behavior rather than inferring rules from another version or returning an empty form;
- a non-active, structurally invalid, or otherwise unusable configuration is not substituted into the response. The implementation reuses the existing configuration-domain error semantics, including `CONFIGURATION_NOT_ACTIVATABLE` where validation exposes an invalid active structure.

Draft and historical configurations are never emitted as selectable form definitions. Omitted rules mean `NOT APPLICABLE`; they are not emitted as optional fields.

### Measurement projection

Each active configuration Measurement Rule produces one measurement item. Its `definition_id`, `code`, `name_en`, `name_ar`, and `default_unit_code` come from the referenced Measurement Definition. `required` is true exactly when rule `requirement` is `REQUIRED`; `primary` is the rule's `is_primary`; `sort_order` is the rule sort order. The response does not invent numeric range, precision, persistence, or completeness metadata.

### Attribute projection and ENUM options

Each active configuration Attribute Rule produces one attribute item. Its definition identity, code, localized names, and `data_type` come from the referenced Attribute Definition; `required` and `sort_order` come from its rule. Supported catalog data types remain `INTEGER`, `DECIMAL`, `BOOLEAN`, `TEXT`, `ENUM`, and `DATE`.

`options` is an empty array for every non-`ENUM` definition. For `ENUM`, it contains only active options owned by that same Attribute Definition, each with `id`, `code`, `name_en`, `name_ar`, and `sort_order`. No option from another definition, and no inactive option, is exposed. An ENUM configuration that has no active option is a configuration-domain validation failure, not an alternate free-text control.

## 4. Core property-profile bootstrap response

`GET /property-profile/core-form` supplies bounded, core catalog-driven selection data before a Unit Type has been selected. Its conceptual response is:

```json
{
  "categories": [{ "id": 0, "code": "RESIDENTIAL", "name_en": "Residential", "name_ar": "...", "sort_order": 10 }],
  "unit_types": [{ "id": 0, "code": "APARTMENT", "name_en": "Apartment", "name_ar": "...", "property_category_id": 0, "sort_order": 10 }],
  "geography": { "countries": [{ "id": 0, "code": "EGYPT", "name_en": "Egypt", "name_ar": "...", "sort_order": 10 }] },
  "development": { "developers": [{ "id": 0, "code": "...", "name_en": "...", "name_ar": "...", "sort_order": 10 }] }
}
```

Only active selectable records are returned. Categories and Unit Types are included because they are bounded canonical catalogs; the client can filter the provided Unit Types by `property_category_id`. Geography includes root Country rows only. Development includes Developer rows only. Child geography, Projects, and Phases are deliberately not eagerly loaded: the future UI uses existing filtered read endpoints after its parent selection. The baseline currently has Egypt and its Governorates, and zero Developers, Projects, and Phases; empty bounded lists are valid responses.

The core response does not create a Property, state or infer a selected Unit Type, embed Unit Type rules, calculate completeness, fabricate persistence fields, or expose a frontend layout schema. The future Property Profile persistence contract decides which core values are submitted and validated.

## 5. Ordering, bounded reads, and privacy

Where the current read model persists `sort_order`, returned collection items use ascending `sort_order`, then ascending stable `id` as the tie-breaker. Where `sort_order` does not exist, the projection uses the existing repository/domain deterministic canonical ordering, with its supported stable ID or code fallback. BF014.6 neither implies that every catalog entity has `sort_order` nor requires a schema change. Parent/child relationship fields use canonical identifiers, never localized labels as identity.

The Unit Type projection must be a bounded aggregate read with no per-rule or per-option query. Its implementation target is no more than eight database queries: Unit Type/category and active configuration discovery plus the aggregate's bounded rule, definition, and batched option reads. The core bootstrap similarly uses a fixed number of collection queries, not a query per Category, Unit Type, Country, or Developer. Exact query counts are implementation acceptance evidence, but N+1 behavior is prohibited.

These projections expose only public canonical catalog metadata needed for form selection. They contain no Organization-private proposal data, Property values, ownership data, user data, audit rows, or hidden provenance-based authority.

## 6. BF014.6A read-model support

BF014.6A is **IMPLEMENTED AND VERIFIED / CLOSED**. Existing persistence reads provide Unit Type and Category lookup, active configuration lookup, complete ordered rule reads, batch Measurement and Attribute Definition reads, active Category and Unit Type lists, active root-Country reads, and active Developer lists. The added projection-specific `listActiveAttributeOptionsForDefinitions(array $definitionIds)` read returns active options for the supplied Definition IDs in one ordered batch without changing the complete historical option read used by configuration administration.

The approved future `GET /unit-types/{id}/property-form` plan is bounded to eight reads:

1. Unit Type by ID.
2. Its Property Category by canonical ID.
3. Active Configuration for that Unit Type.
4. Ordered Measurement Rules for the Configuration.
5. Referenced Measurement Definitions in one batch.
6. Ordered Attribute Rules for the Configuration.
7. Referenced Attribute Definitions in one batch.
8. Active Attribute Options for referenced Attribute Definition IDs in one batch.

This plan contains no per-rule, per-definition, or per-option reads. The existing core-form reads remain active Categories, active Unit Types, active root Countries, and active Developers as independently bounded lists.

## 7. BF014.6B Unit Type projection service

BF014.6B is **IMPLEMENTED AND VERIFIED / CLOSED**. `PropertyFormProjectionService` is a read-only, frontend-neutral service composed from the catalog, configuration, Measurement Definition, and Attribute Definition repositories. It returns `null` for a missing Unit Type, rejects an inactive Unit Type for new entry with `CATALOG_ITEM_INACTIVE`, and rejects an active Unit Type without an active Configuration with `NO_ACTIVE_CONFIGURATION`.

The service maps rule-owned requiredness, primary status, and ordering with canonical definition identity, labels, semantic type, and default measurement unit. It uses only active batch-loaded ENUM options, keeps non-ENUM options empty, rejects an unusable ENUM with `ENUM_HAS_NO_ACTIVE_OPTIONS`, and treats missing or duplicate referenced definitions as `CONFIGURATION_NOT_ACTIVATABLE`. It does not authorize, mutate, start transactions, choose HTTP status codes, or persist Property data.

Focused real-MariaDB acceptance verified APARTMENT, VILLA, RESIDENTIAL_LAND, and COMMERCIAL_UNIT against the seeded configuration matrices; active-only configuration behavior; draft and historical isolation; unavailable-state errors; active-option filtering; deterministic ordering; and the eight-query bounded plan.

## 8. Submission boundary

This contract projects a form definition only. A later Property Profile unit owns request payloads, typed value validation, option ownership validation, version persistence, progressive save behavior, completeness, and authorization for Property mutation. Client validation is convenience only; it cannot replace server validation against the current persisted canonical rules.
