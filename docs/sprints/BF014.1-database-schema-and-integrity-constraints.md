## D. Physical conventions

- MariaDB 10.4.32 target; InnoDB; utf8mb4 / utf8mb4_unicode_ci.
- BIGINT UNSIGNED AUTO_INCREMENT internal primary keys.
- Application-generated CHAR(26) ULIDs on approved domain resources.
- Nullable created_by_user_id and updated_by_user_id FKs on catalog/configuration/rule rows; nullable applied_by_user_id on the seed ledger. NULL means system/seed operation; a non-NULL ID attributes an authenticated human through users.id.
- No fake or dedicated System User is required. Nullable actors and the ULID omissions below are locked BF014 exceptions to generic guidance.
- Every FK uses ON DELETE RESTRICT and ON UPDATE RESTRICT; no CASCADE or SET NULL.
- Named indexes and CHECK constraints; nullable generated PERSISTENT uniqueness guards.
- Mutable rows use created_at/updated_at TIMESTAMP conventions. The append-only seed ledger has applied_at and no updated_at.
- Machine-code trim/uppercase normalization belongs to later Services; no special ASCII or case-sensitive collation was introduced. CHECK comparisons use the locked Unicode collation, not byte-exact casing enforcement.

## F. Catalog status and provenance

Canonical catalog statuses are active and inactive. Configuration statuses are draft, active, and historical. Catalogs and configurations distinguish SYSTEM_SEED and SYSTEM_ADMIN provenance.

Rules inherit configuration lifecycle/provenance and do not duplicate status/provenance columns. The seed ledger also has neither column. Provenance is not authorization, and seeded-record hard-delete prohibition is a later Service/business invariant, not DB enforcement provided by the provenance CHECK alone.

## G. Configuration integrity

The database enforces unique(unit_type_id, version_number), version_number > 0, and at most one ACTIVE Configuration Version per Unit Type. active_unit_type_guard is a nullable generated PERSISTENT column containing unit_type_id only when active, with a UNIQUE index.

Architectural lifecycle is DRAFT -> ACTIVE -> HISTORICAL. Version numbers are never reused. Once activated, structural configuration is immutable; historical configuration is not directly reactivated. Restoring previous structure requires a new Configuration Version.

These transition, allocation, and immutability semantics belong to later Services. BF014.1 implements DB uniqueness/guards, not transition enforcement or Property assignment.

## H. Measurement integrity

BF014 V1 default/allowed unit is SQM, enforced by a CHECK. No unit relation table exists in BF014.1. The future Property measurement value contract is DECIMAL(18,4), with decimal-string API semantics planned; no Property measurement value table was created.

Measurement Rules enforce unique(configuration_version_id, measurement_definition_id), REQUIRED/OPTIONAL requirements, a 0/1 is_primary flag, and primary-implies-REQUIRED. primary_configuration_guard is nullable generated PERSISTENT with a UNIQUE index, allowing at most one primary Measurement per Configuration.

Zero primary is legal: the locked OTHER baseline configuration has none. This is a baseline contract statement, not a claim that OTHER or any other baseline data was inserted.

## I. Attribute integrity

Supported definition types are INTEGER, DECIMAL, BOOLEAN, TEXT, ENUM, and DATE. Minimal validation metadata is nullable text_max_length; a non-NULL value must be positive and only belongs to TEXT. No arbitrary validation JSON, regex, component metadata, or numeric/date bounds were added.

Attribute Rules enforce unique(configuration_version_id, attribute_definition_id) and REQUIRED/OPTIONAL. No rule means NOT APPLICABLE. Attribute Option code is unique within its Definition, not globally. ENUM-parent semantic validation and published Definition structural immutability belong to later Services.

## J. Geography integrity

Supported types are COUNTRY, GOVERNORATE, CITY, AREA, and DISTRICT. Code is globally unique. COUNTRY requires no parent; non-COUNTRY requires a parent. The parent FK restricts deletion/update.

Hierarchy is flexible, with no rigid level-depth constraint. No trigger or stored procedure enforces ancestry cycles. Self-parent and ancestry-cycle validation remain later Service responsibilities.

## K. Development catalogs

Developer has a global canonical code. Project has a global canonical code, nullable developer_id, and nullable geographic_location_id. Nullable relationships still use RESTRICT when referenced.

Phase requires a Project and has code uniqueness within that Project. No Phase geographic override exists. No Developer, Project, or Phase baseline data was inserted.

## L. Seed ledger

property_catalog_seed_versions tracks successful future canonical seed-package application using an internal id, unique seed_key, SHA-256 checksum, applied_at, and nullable applied_by_user_id. It has no ULID, status, provenance, or updated_at. CHECKs reject blank keys and invalid checksum shape.

BF014.1 creates tracking infrastructure only. Seed runner and baseline seed packages belong to BF014.5. Successful-only tracking, atomic package execution, checksum comparison, and idempotent/non-destructive reruns are future runner responsibilities, not implemented behavior of an empty table.
