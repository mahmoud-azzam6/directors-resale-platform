## Objective and dependencies

BF014.4 defines the authorization and HTTP boundary for the canonical catalog Services delivered by BF014.3. It depends on BF010 authentication, BF012 Position-derived Permission authorization, BF013 HTTP conventions, and BF014.1-BF014.3. It adds no domain behavior: controllers validate transport shape, authorize, invoke the existing Service, and map its result or error.

The implementation uses route registration in `routes/api.php`, the existing authentication/authorization wrappers, `AuthorizationMiddleware`, `AuthorizationService`, controller DI through the service container, and the existing JSON `Response` conventions. Controllers must never call a repository directly, duplicate Service validation, own a transaction, or implement locking.

## Locked authorization rules

| Operation | Capability | Scope |
| --- | --- | --- |
| All catalog reads | `property_catalogs.view` | Authenticated authorized consumer; no Organization target or `SYSTEM_ONLY` restriction |
| All catalog/configuration mutations | `property_catalogs.manage` | `SYSTEM_ONLY` |

`property_catalogs.manage` is platform-catalog authority only. It is not granted by Organization ownership, Franchise or Partner Agency administration, Position name, or frontend state. A System Organization User still requires the assigned active capability. A Franchise or Partner Agency User cannot mutate canonical catalog data, even with a similarly named Position.

Read routes use the existing authorization wrapper with `property_catalogs.view` and no target resolver. Mutations use the same wrapper with `property_catalogs.manage` and `OrganizationScopeService::SYSTEM_ONLY`. Authentication failure remains 401; an authenticated caller lacking the capability or required scope receives 403.

## Permission-catalog requirement

The current Permission catalog contains no `property_catalogs.view` or `property_catalogs.manage` code. BF014.1 intentionally added no Permission capability, and neither capability may be assumed to exist at runtime.

BF014.4A must add one additive migration after migration 031 to insert the two active, controlled Permission catalog rows, following the established migration-based catalog pattern. The migration must preserve global code uniqueness and must not add runtime Permission-definition CRUD, direct User permissions, role logic, or a new authorization system. Assignment remains the existing Position-to-Permission mechanism; the established explicit bootstrap/authorized assignment flow applies after the capabilities exist.

## Route and controller contract

Routes follow the existing plural, unversioned resource paths registered by `routes/api.php`; the application routing layer supplies its existing API boundary. IDs are the existing Service identifiers. List query parameters are passed only as supported repository/service options (`status`, `search`, `page`, `per_page`, and supported ordering); no second query model is introduced.

| Family | Read routes (`property_catalogs.view`) | Mutation routes (`property_catalogs.manage` + `SYSTEM_ONLY`) | Service boundary |
| --- | --- | --- | --- |
| Property Categories | `GET /property-categories`; `GET /property-categories/{id}` | `POST /property-categories`; `PUT /property-categories/{id}`; `POST /property-categories/{id}/deactivate`; `POST /property-categories/{id}/reactivate`; `DELETE /property-categories/{id}` | `PropertyCatalogService` category operations |
| Unit Types | `GET /unit-types`; `GET /unit-types/{id}` | `POST /unit-types`; `PUT /unit-types/{id}`; explicit deactivate/reactivate; `DELETE` | `PropertyCatalogService` Unit Type operations |
| Measurement Definitions | `GET /measurement-definitions`; `GET /measurement-definitions/{id}` | `POST`; `PUT /{id}`; explicit deactivate/reactivate; `DELETE` | `PropertyCatalogService` Measurement Definition operations |
| Attribute Definitions and Options | `GET /attribute-definitions`; `GET /attribute-definitions/{id}`; `GET /attribute-definitions/{definitionId}/options`; `GET /attribute-options/{id}` | Definition `POST`, `PUT`, explicit deactivate/reactivate, `DELETE`; nested Option `POST`, `PUT`, explicit deactivate/reactivate, `DELETE` | `PropertyCatalogService` Attribute Definition and Option operations |
| Geographic Locations | `GET /geographic-locations`; `GET /geographic-locations/{id}`; `GET /geographic-locations/{id}/children` | `POST`; `PUT /{id}`; explicit deactivate/reactivate; `DELETE` | `GeographicLocationService` |
| Developers | `GET /developers`; `GET /developers/{id}` | `POST`; `PUT /{id}`; explicit deactivate/reactivate; `DELETE` | `DevelopmentCatalogService` Developer operations |
| Projects | `GET /projects`; `GET /projects/{id}` | `POST`; `PUT /{id}`; explicit deactivate/reactivate; `DELETE` | `DevelopmentCatalogService` Project operations |
| Project Phases | `GET /projects/{projectId}/phases`; `GET /project-phases/{id}` | `POST /projects/{projectId}/phases`; `PUT /projects/{projectId}/phases/{phaseId}`; explicit deactivate/reactivate; `DELETE` | `DevelopmentCatalogService` Phase operations |

`explicit deactivate/reactivate` means `POST /resource/{id}/deactivate` and `POST /resource/{id}/reactivate`, preserving the established action-route convention. The controller supplies the authenticated actor ID only where the Service accepts it. Request bodies contain only the corresponding Service input; identity, provenance protection, parent/reference eligibility, lifecycle, safe-delete and hierarchy validation remain Service-owned.

## Configuration lifecycle and rule routes

Configuration routes are nested under their Unit Type and always invoke `UnitTypeConfigurationService`.

| Route | Operation |
| --- | --- |
| `GET /unit-types/{unitId}/configurations` | List configurations for the Unit Type |
| `GET /unit-types/{unitId}/configurations/{configurationId}` | Return the existing configuration aggregate, including rule structure required for administration |
| `POST /unit-types/{unitId}/configurations/drafts` | Create a blank DRAFT |
| `POST /unit-types/{unitId}/configurations/drafts/clone-active` | Clone the current ACTIVE configuration into a DRAFT |
| `POST /unit-types/{unitId}/configurations/{configurationId}/activate` | Activate the DRAFT |
| `DELETE /unit-types/{unitId}/configurations/{configurationId}` | Delete an eligible DRAFT |
| `POST /unit-types/{unitId}/configurations/{configurationId}/measurement-rules` | Add Measurement Rule |
| `PUT /unit-types/{unitId}/configurations/{configurationId}/measurement-rules/{ruleId}` | Update Measurement Rule |
| `DELETE /unit-types/{unitId}/configurations/{configurationId}/measurement-rules/{ruleId}` | Remove Measurement Rule |
| `POST /unit-types/{unitId}/configurations/{configurationId}/attribute-rules` | Add Attribute Rule |
| `PUT /unit-types/{unitId}/configurations/{configurationId}/attribute-rules/{ruleId}` | Update Attribute Rule |
| `DELETE /unit-types/{unitId}/configurations/{configurationId}/attribute-rules/{ruleId}` | Remove Attribute Rule |

All configuration reads require `property_catalogs.view`; every lifecycle and rule mutation requires `property_catalogs.manage` plus `SYSTEM_ONLY`. BF014.3 exposes no supported configuration metadata update, so BF014.4 defines none. It must not expose generic configuration status PATCH, ACTIVE-to-DRAFT, HISTORICAL-to-ACTIVE, or HISTORICAL mutation.

## Responses, errors, and concurrency

Controllers use the existing JSON success/error response shape and established not-found handling. A Service `null` result maps to the project-standard 404 response for a requested resource. Transport-shape validation follows existing controller conventions and returns the existing validation response; controllers do not repeat domain eligibility checks.

The route/controller error boundary is:

| Condition | HTTP result |
| --- | --- |
| Missing or invalid authentication | 401 |
| Authenticated caller missing `property_catalogs.*` capability or required System scope | 403 |
| Requested resource absent under the existing resource convention | 404 |
| Service business conflict or invalid transition/reference/structure | Existing BF013 response mapping, retaining the machine-readable BF014.3 domain code |
| Invalid transport body/query | Existing validation mapping |
| Unexpected failure | Existing safe internal-error response; no SQL, deadlock, stack trace, or repository detail |

BF014.4 does not create an error framework or decide concurrency in HTTP. Unit Type serialization, configuration allocation/activation/rule locking, geography root-first locking, development locks, transactions and rollback remain entirely in BF014.3 Services. Controllers make one Service call and map its outcome.

## DI and implementation boundaries

BF014.4 implementation registers dedicated catalog/configuration/geography/development controllers and their Service dependencies through the existing service container, then registers the routes in `routes/api.php` through the established authorization wrapper. Repository bindings remain persistence-only and are unavailable to controllers as an implementation boundary. No middleware bypass, frontend check, or request-supplied Organization value may substitute for `SYSTEM_ONLY` authorization.
